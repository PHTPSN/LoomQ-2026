03 · Quantum basics

Eight ideas take you
from vectors to circuits.

Start with linear algebra: a quantum circuit multiplies a complex vector by matrices. Measurement then returns a bit string at random, using the squared magnitudes of the vector coordinates as probabilities.

01 / VECTOR

A qubit is a vector

One qubit is represented by a length-2 complex vector called its state. |ψ⟩ is simply a name for that vector. The fixed vectors |0⟩=[1,0]ᵀ and |1⟩=[0,1]ᵀ form the computational basis: the two results a measurement can report.

|ψ⟩ = α|0⟩ + β|1⟩ = [α, β]ᵀ
02 / NUMBER

Amplitudes become probabilities

The complex numbers α and β are called amplitudes. They are not probabilities. Measuring 0 has probability |α|²; measuring 1 has probability |β|². A valid state has total probability one. A state with multiple nonzero amplitudes is called a superposition of those basis vectors.

|α|² + |β|² = 1
03 / MEMORY

More qubits mean more coordinates

Two qubits use a length-4 vector whose coordinates are named |00⟩, |01⟩, |10⟩, and |11⟩. Combining independent qubits uses the Kronecker product, written ⊗: multiply every coordinate of the first vector by every coordinate of the second. Each added qubit doubles the vector length.

[a,b]ᵀ ⊗ [c,d]ᵀ = [ac,ad,bc,bd]ᵀ
04 / PROGRAM

A gate is a matrix

A gate updates the state by matrix multiplication. Its matrix is unitary: U†U=I, where U† is the conjugate transpose. This preserves vector length, and applying U† undoes U. A circuit is the ordered program of these matrix operations.

|ψ′⟩ = U|ψ⟩
05 / COMBINE

Phase controls interference

A complex amplitude has a magnitude and an angle; the angle is its phase. Phase does not change that coordinate's probability by itself. Later gates can add coordinates: aligned amplitudes reinforce, while opposite amplitudes cancel. This is interference.

1/√2 + (−1/√2) = 0
06 / READ

Measurement chooses one result

Measurement randomly selects one computational-basis label, such as 00 or 11. The probability is the squared magnitude of that label's coordinate. It returns the selected label as an ordinary bit string; after that read, the state equals the selected basis vector.

coordinate a₁₁ → P(11) = |a₁₁|²
07 / REPEAT

One shot is one complete run

For one shot, the program creates fresh qubits in |0…0⟩, applies every gate in order, and measures once. N shots restart this whole process N times. “Counts” is the map from each returned bit string to how often it appeared.

counts = { "00": 503, "11": 521 }
08 / JOINT

Entanglement is non-factorability

A multi-qubit state is entangled when it cannot be written as a Kronecker product of separate single-qubit states. In the Bell state below, neither qubit has its own independent vector, so measuring one bit constrains the other.

|Φ⁺⟩ = (|00⟩ + |11⟩)/√2

The definitions in action

Calculate a Bell pair

A Bell pair is an entangled two-qubit state whose measured bits are perfectly correlated: this example returns only 00 or 11, each with probability 1/2. To calculate it, write labels in |q₁q₀⟩ order. H gives q₀ two amplitudes of 1/√2, and CX flips q₁ only in the coordinate where q₀=1.

  1. INITIALIZE|q₁q₀⟩ = |00⟩Both qubits start at 0
  2. APPLY H TO q₀(|00⟩+|01⟩)/√2Two nonzero coordinates
  3. APPLY CX(|00⟩+|11⟩)/√2Cannot factor into two vectors
  4. MEASUREP(00)=P(11)=1/2Only matching bits appear
One important convention

In result key “10”, the rightmost character is c[0]. LoomQ normalizes every backend to this little-endian convention.

06 · Hybrid compiler

Quantum operations in order.
Classical decisions in RISC-V.

Hybrid-QASM adds one classical { … } block to an OpenQASM 2.0 circuit. LoomQ separates the two responsibilities: quantum gates and measurements remain an ordered operation stream, while integer assignments and if/else decisions become deterministic RISC-V instructions.

01Read Hybrid-QASM

Ordinary quantum instructions surround one classical block. Measurement expressions use c[n]; writable integer values use r1, r2, and so on.

02Preserve quantum order

Gates and measurements are normalized into the same canonical instruction order used by the circuit translator.

03Lower classical logic

Measured bits enter RISC-V registers x10, x11, and onward. Assignments and branches compile into a small, executable assembly program.

Compilation is deterministic and local: it does not call the AI model or a cloud service.

Real-machine tutorial

Learn one safe workflow for each platform.

The website never submits hardware. These lessons explain what each step means, which project resource helps, and exactly where a read-only action becomes a quota-consuming cloud submission.

The rule shared by all three platforms

First run the circuit in a local simulator. Then refresh the real device’s current status, check its supported qubit count and gates, review price or quota, and obtain the account owner’s approval. Credentials belong only in ignored local configuration—not in this page, screenshots, evidence files, or Git.

ORIGIN QUANTUM

From a locally checked circuit to one saved hardware job

A backend is the named machine that receives your circuit. A preflight reads the available backend list before submission; it does not consume hardware quota.

  1. Validate the circuit locally

    Use the Vendor simulators page first. Then use its optional translation panel to inspect the Origin Quantum form before contacting the cloud.

  2. Configure account access

    Create a current API token in the Origin Quantum account center. A token is a secret used by software; it is different from your website password. Put it only in the ignored repository-root .env file.

    LOOMQ_ORIGINQ_API_TOKEN=<your-current-api-token>
LOOMQ_ORIGINQ_BACKEND=<an-online-backend-id>
  3. Build once, then run a read-only preflight

    The isolated image keeps the cloud SDK separate from the competition environment. Preflight confirms that the token works and shows the currently available machines.

    docker build -f starter_kit/hardware/Dockerfile.originq `
  -t loomq-originq-hardware:0.4.0 .

docker run --rm --env-file .env `
  --mount type=bind,source=${PWD},target=/workspace/repo `
  loomq-originq-hardware:0.4.0 preflight
  4. Approve, submit once, and keep the job ID

    Only submit after checking the selected machine and quota. The project’s helper requires an explicit confirmation flag, saves the returned job ID immediately, and refuses to overwrite an existing record.

    docker run --rm --env-file .env `
  --mount type=bind,source=${PWD},target=/workspace/repo `
  loomq-originq-hardware:0.4.0 submit --confirm-real-hardware

docker run --rm --env-file .env `
  --mount type=bind,source=${PWD},target=/workspace/repo `
  loomq-originq-hardware:0.4.0 poll --wait
Want to reproduce the archived evidence example?

Use starter_kit/circuits/bell.qasm, the default bell profile, backend WK_C180, and 512 shots. Run the prepare command before submission. For the three-qubit example, add --profile ghz3 to prepare, submit, and poll.

SPINQ CLOUD

Prepare a cloud-compatible circuit before choosing a machine

SpinQ’s cloud hardware measures used qubits automatically, so its submitted artifact must omit explicit measure statements even though the local learning circuit contains them.

  1. Start with a locally verified OpenQASM circuit

    Run it through the SpinQit simulator on the Vendor simulators page. Simulation checks circuit meaning, but it does not prove that a real machine is currently online.

  2. Refresh machines and choose by capability

    Connect the authenticated SpinQ cloud tool, call get_platforms, and select an online machine with enough qubits and the required gates. Save that fresh response as your preflight JSON.

  3. Create the exact submission artifact

    The project helper checks the selected platform and removes cloud-incompatible measurement declarations. Inspect its output before sending it anywhere.

    python -m starter_kit.hardware.spinq_cloud `
  --source starter_kit/circuits/bell.qasm `
  --platforms-json <fresh-preflight.json> `
  --platform <online-platform-code> `
  --out <prepared-cloud-circuit.qasm>
  4. Approve one submission, then retrieve that same task

    Call qasm_submit with the selected platform code and the exact prepared QASM only after approval. Save the returned task ID, wait, and use get_task_result_by_id; never create a second task merely because the first is pending.

AMAZON BRAKET

Separate free local learning from an authorized AWS QPU task

A QPU is a physical quantum processing unit. Amazon Braket local simulation needs no AWS account, while a QPU task needs AWS access, a region, service configuration, storage, and explicit cost approval.

  1. Translate and test locally without credentials

    Use the Vendor simulators page for Amazon Braket, or run the repository example below. It teaches the OpenQASM 3.0 program shape and returns counts without contacting AWS.

    python starter_kit/examples/run_braket.py
  2. Create a named AWS profile with limited permissions

    For learning and device discovery, begin with an identity that can only call SearchDevices and GetDevice. Those read-only permissions cannot create a quantum task.

    py -m pip install -r requirements/backend-observations.lock.txt
$env:AWS_PROFILE = "loomq-readonly"
py scripts/backend_observations.py --provider aws `
  --output .cache/loomq/backend-observations.json
  3. Read the fresh report before choosing a QPU

    Check the device ARN, region, ONLINE status, qubit count, capabilities, queue information, and current public pricing. An ARN is AWS’s unique identifier for a cloud resource.

  4. Stop at the project boundary before paid submission

    This repository intentionally has no AWS QPU submission helper and no archived AWS hardware job. After the account owner approves service enablement, storage, region, device, and cost, follow the official Braket console or SDK task workflow. Do not treat read-only discovery credentials as submission permission.

What the project provides

OpenQASM 3.0 translation, a credential-free local Braket example, and read-only live device discovery. It does not automate a chargeable AWS task.

GPU Tutor

Follow one GHZ program through five transformations.

Select a step to see what changes, what stays invariant, and which artifact proves it.

Input

Start with operations, not hardware details.

The GHZ circuit creates a three-qubit superposition with H and two CX gates, then measures every qubit. L3 preserves these operations in order.

h q[0];
cx q[0], q[1];
cx q[1], q[2];
measure q[0] -> c[0];
measure q[1] -> c[1];
measure q[2] -> c[2];
Encode

Each operation becomes one unsigned 32-bit word.

The low seven bits carry custom-0 opcode 0x0B. Base gates use funct7; operands use rd, rs1, and rs2.

0x0200000b  h q[0]
0x0e00800b  cx q[0], q[1]
0x0e01008b  cx q[1], q[2]
0x1400000b  measure q[0] -> c[0]
Decode

Fields are validated before semantics are recovered.

Opcode selects the extension, funct3 selects the format, and funct7 or the immediate identifies the operation. Invalid opcodes, unknown functions, repeated qubits, and nonzero reserved fields are rejected.

31…25funct724…20rs219…15rs114…12funct311…7rd6…00x0B
Execute

Decoded gates drive raw GPU kernels.

CuPy compiles CUDA C kernels at runtime through NVRTC. The archived run applies decoded H and CX operations to a complex state vector, then derives measurement probabilities on a Tesla P100.
